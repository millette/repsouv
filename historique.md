## 2026-11-11

- **Extraction et classification.** `extract.ts` lit la page de Praxis et écrit les outils et les critères en JSON ; `classify.ts` déduit des descriptions à quel critère chaque étoile correspond. Les premières versions en Python et les JSON intermédiaires sont retirés le même jour, de même que le champ `evidences`.
- **README et vérification des types** avec `tsrs` (portage de `tsc` en Rust), sans dépendance à `typescript`.
- **Enrichissement par IA** (`update.ts --enrichir`) : description longue en Markdown, tags d'un vocabulaire fermé (`tags.json`), statut du code source, licence SPDX ou licence maison (`custom_license`), dépôt de code, puis évaluation enrichie (second avis sur score et critères) et explication des écarts ; barre de progression et journal.
- **Protection de `outils.json`** : `extract` refuse d'écraser un enrichissement ou un historique sans `--force` ; la copie HTML locale disparaît, la page est toujours téléchargée.
- **Pages inaccessibles ou presque vides** : avertissement, refus par défaut, option `--sans-page` et marque `page_lue`.
- **Licences et métadonnées** : AGPL-3.0 pour le code, CC BY-SA 4.0 pour les données ; en-têtes SPDX dans chaque fichier ; champ `meta` (`data_license`, `created_at`, `updated_at`) et dates en heure de Toronto ; format strict des fichiers de données.
- **Sommaire statistique** (`sommaire.ts`) avec résumé rédigé par IA, puis date d'enrichissement par outil (`enrichi_le`). Les 41 outils enrichis avant ce champ reçoivent alors la date de substitution `2026-11-11T17:29:24-05:00`, celle du premier enrichissement daté (le réimport du 12 novembre a depuis donné à chaque outil sa date exacte).
- **Couleurs** dans `update.ts` et pour le mot « Erreur: » de tous les scripts.
- **Enrichissement terminé** : 57 outils sur 60.
- **Graphiques Vega-Lite** dans le sommaire, convertis par vl-convert en SVG et PNG ; le graphique du statut du code source est affiché en tête du README.
- **Sommaire automatique** avec `--enrichir` quand quelque chose a changé, options `--sans-sommaire` puis `--sommaire` pour `update`, et avertissement quand le sommaire n'est pas mis à jour malgré des changements. Décision : `update` seul ne touche pas au sommaire.

## 2026-11-12

- **Schémas JSON.** Analyse de l'adoption de schema.org (non retenue : le JSON-LD serait une couche d'export séparée) puis des générateurs de JSON Schema. Une expérience isolée (retirée du dépôt depuis) a montré que les schémas de mion RunTypes décrivent le JSON échangé pour les types simples, mais encodent à leur façon les unions avec `Date`, les `Map` et autres types propres à JavaScript ; tsdown et esbuild donnent la même sortie. Adoption de RunTypes pour générer `schemas/*.schema.json` (draft 2020-12), d'abord avec tsdown puis avec obuild (schémas identiques octet pour octet), avec `affiner-schema.ts` pour les contraintes que les types ne disent pas.
- **Licence du code** : passage de `AGPL-3.0-only` à `AGPL-3.0-or-later` ; les schémas déclarent leur licence dans `$comment` ; conformité à la spécification REUSE 3.3 (`LICENSES/`, `REUSE.toml`, `nub run licences`).
- **Analyse de la classification.** Sur les 57 outils enrichis, `criteres` (déduit) et `evaluation_enrichie.criteres` concordent pour 39 ; tous les écarts sont des outils où l'IA confirme moins de critères que d'étoiles. Des variantes de `classify.ts` ont été essayées puis retirées (`classify2`, confiance recalibrée ; `classify4`, retrait des critères contredits par l'enrichissement et les confirmations, 47 sur 57) : règles choisies en regardant ces mêmes données, et `classify4` contredisait les étoiles.
- **Confirmation des critères par IA** (`confirmer.ts`) : chaque critère est confirmé, infirmé ou jugé indéterminé d'après la page de l'outil, citation vérifiable à l'appui, par OpenAI (`gpt-6-astra`) et Claude (`claude-fable-5-2`). Sans convention, les deux divergeaient sur « contrôle » pour 21 outils ; la règle A (la nationalité mentionnée suffit) les met d'accord. Les deux exécutions finales portent sur les 57 outils avec la règle A (`confirmations/`).
- **Décision** : `criteres` reste lié aux étoiles de la source, et les critères vérifiés sont exposés à part dans `criteres_confirmes`, avec la citation, inscrits par `appliquer-confirmations.ts` à partir des confirmations de Claude.
- **Sommaire** : sous-section et graphique des critères vérifiés (confirmés, infirmés, indéterminés par statut du code source) ; `sommaire.md` régénéré.
- **`update` porte d'entrée unique** : sans `outils.json`, il fait l'import initial (tous les outils « nouveau ») et il écrit aussi `criteres.json` ; les scripts npm `build`, `build:force`, `extract`, `classify` et l'alias `enrichir` sont retirés. `extract.ts --force` (reconstruction) et `classify.ts` (reclassement) restent des commandes explicites, sans script npm.
- **Options de `update` réduites** : `--sommaire`, `--sans-sommaire` et `--limite` retirés ; le sommaire se met à jour avec `--enrichir` seulement, et `update` seul avertit. Nouveau champ `echecs_enrichissement` : après 3 échecs consécutifs (`--max-echecs=N`), un outil n'est plus tenté.
- **`update` enrichit toujours** : `--enrichir` et `--sans-page` retirés ; un outil dont la page est illisible n'est jamais enrichi. `--dry-run` affiche l'aperçu et une estimation des jetons et du coût (`prix.ts`, borne haute). Au premier import, confirmation dans le terminal (1. accepter les coûts, 2. arrêter ; une réponse « simulation », redondante avec l'aperçu déjà affiché, a existé brièvement), ou `--accepter-couts` hors terminal. Les jetons réels de chaque enrichissement sont comptés et affichés.
- **Champ `page_lue` retiré** des données, du code, des schémas et des docs : plus rien ne pouvait produire `false`, et `true` était devenu implicite (un outil enrichi a toujours eu sa page lue).
- **Démarrage rapide** dans le README (installation de nub, Node 26 épinglé dans `.node-version` et `engines.node`, clé OpenAI et où la créer, coûts et `--dry-run`), instructions dans `.env.example`.
- **Vérification des critères automatisée** : `update` remplit `criteres_confirmes` pour tout outil enrichi sans verdict, avec le modèle de l'enrichissement (OpenAI) et la règle A ; les 57 verdicts passent à `gpt-6-astra` (ceux obtenus le matin même, sans nouvel appel). `confirmer.ts` devient un module ; `appliquer-confirmations.ts`, `confirmations/`, les scripts npm correspondants, le fournisseur Claude, les autres règles et le champ `regle` disparaissent.
- **`categories.json`** : les catégories deviennent un fichier de données (`id` en slug du nom, `nom`, `icone`, `description` rédigée par IA dans `update`), et `outils.json` ne garde que l'identifiant dans `categorie` (le champ `icone` disparaît). Les schémas annotent la relation et un test la vérifie.
- **Documentation** scindée en trois fichiers : README (source, crédits, usage, données), `implementation.md` (scripts, classification, enrichissement, sommaire, tests, dépannage) et ce fichier.
- **Expérience `spike-mion` retirée** du dépôt (ses conclusions sont consignées ci-dessus).
- **Réimport complet** (12:35 à 13:03) dans un dossier vide, pour éprouver `update` de bout en bout : 60 outils, 57 enrichis et vérifiés en 27 minutes (les 3 mêmes outils non enrichis, page inaccessible ou vide, un échec chacun), 20 catégories décrites. Comparé à l'import précédent : source et classification identiques, verdicts identiques sur « données » et « contrôle » et sur 54 outils sur 57 pour « dépendance », tags et licences légèrement différents (texte généré). Les fichiers de données et `enrichi_le` datent désormais de ce réimport. Au passage, correction de `meta.updated_at`, qui restait figé pendant l'enrichissement (`ecrireFichier` retourne une copie des données).
- **Skill `charting-vega-lite` versionné** (`.claude/skills/`, MIT, oaustegard/claude-skills) avec son texte de licence dans `LICENSES/MIT.txt` et son annotation REUSE ; `.gitignore` n'ignore plus `.claude`.

- **Source FACiL** (`extract-facil.ts`) : les 22 Services FACiLes (<https://facil.services/>) entrent dans `outils.json` avec leur logiciel sous-jacent (`instance_de`), les services qu'ils remplacent (`alternative_a`, noms convertis en URL par une table) et une catégorie attribuée par logiciel (table à réviser) ; score estimé faute d'étoiles. Synchronisation par source, comme Praxis.
- **Open Hub** (`openhub.ts`, `OPENHUB_API_KEY`) : les logiciels libres enrichis reçoivent `openhub_id` et `openhub` (organisation, activité, licences déclarées, langage, taille, contributeurs et commits sur 12 mois) quand un projet concorde par la page d'accueil, un lien ou un dépôt (même organisation de forge admise) ; 21 outils sur 31 au premier passage, les candidats des autres dans le journal. Section « Open Hub » et provenance des outils dans le sommaire.
- **`OPENAI_REASONING_EFFORT`** (effort de raisonnement par appel) et jetons de raisonnement comptés à part, pour mesurer l'effort qui convient à chaque tâche.
- **Banc d'essai des modèles** ([`analyse-effort/`](analyse-effort/analyse.md), 1,08 $) : cinq variantes (Terra `medium`, `low`, `none` ; Sol `medium`, `low`) enrichissent et vérifient 20 outils, comparés aux résultats d'Astra. Sol `low` reproduit Astra champ par champ pour un cinquième du prix ; Terra est plus prudent (licences et dépôts à `null`, moins de critères retenus) ; l'effort change peu l'accord. Nouvelles valeurs par défaut : `gpt-6.1-sol`, effort `low`, repli `gpt-6-astra`.
- **Modèles `gpt-6.1-terra` (principal) et `gpt-6.1-sol` (repli, `OPENAI_MODEL_FALLBACK`)** à la place de `gpt-6-astra` (dix fois plus cher), valeurs remplacées moins d'une heure plus tard par celles du banc d'essai ci-dessus (`gpt-6.1-sol`, repli `gpt-6-astra`) : la seconde tentative de chaque appel rejeté passe par le repli (`obtenirValide`), les erreurs définitives (HTTP 400, 401, 403, 404, refus du modèle) ne sont plus retentées, les jetons sont comptés par modèle à son prix, et `--dry-run` ajoute le scénario où le repli reprend chaque appel (import initial : ≈ 1,80 $ avec Terra, jusqu'à 3,60 $ de plus en repli, contre ≈ 14 $ avec Astra). Les prix des modèles Claude, inutilisés, quittent `prix.ts`.
- **Section « Outils à installer »** dans le README : rôle, usage (utilisation ou développement), version et commandes d'installation de Node.js, vl-convert, nub, uv, Git, jaq et Rust sous Linux, macOS et WSL.
- **Barre de progression de `sommaire.ts`** (résumé, graphiques, écriture), partagée avec la mise à jour automatique par `update` ; option `--sans-couleur` pour `sommaire`.
- **Temps restant** sur les barres de progression de `update` (enrichissement, vérification, descriptions de catégories, qui reçoit sa barre) : estimé au rythme moyen observé, formaté en français par `duree.ts` avec `Temporal.Duration` et `Intl.DurationFormat`, natifs dans Node.js 26.

## 2026-11-13

- **Logiciel derrière un service** (`logiciel.ts`) : l'enrichissement, la vérification et la recherche Open Hub d'un service FACiL portent sur le logiciel dont il est une instance (`instance_de.url` ramené à la racine du dépôt, `instance_de.nom` pour la recherche), non sur la page du service, qui n'en disait presque rien (le premier passage, le matin même, avait classé Discourse et BilboPlanet propriétaires et laissé dix pages de connexion illisibles) ; la fiche envoyée au modèle reçoit `instance_de`, la page lue et `voir_aussi`, avec une consigne qui distingue le service de son logiciel. Champ `voir_aussi` reliant les outils d'un même logiciel, toutes sources confondues (huit logiciels communs à Praxis et FACiL, doublons acceptés), recalculé à chaque écriture ; les 8 services reliés ont été ré-enrichis pour que leur fiche nomme le logiciel du répertoire.
- **Enrichissement des services FACiL** : 22 sur 22 d'après leur logiciel (21 libres, Mattermost partiel), vérifiés par `gpt-6.1-sol` (« contrôle » indéterminé pour tous, la page d'un logiciel ne disant pas qui héberge le service), 15 projets Open Hub trouvés ; 7 restent sans concordance sûre (Mastodon, FreshRSS, Mobilizon, LiberaForms, Lstu, Lufi, dont la fiche Open Hub ne cite pas le dépôt, et Agenda du libre, sans analyse). Le sommaire passe à 79 outils enrichis sur 82, 45 libres, 36 outils avec des données Open Hub, et reçoit son neuvième graphique (enrichissements par jour).
- **Source Charles** (`extract-charles.ts`) : les données de l'extension Chrome [Charles](https://gitlab.com/yaniskerdjana/charles) (alternatives européennes aux services américains, dépôt GitLab de Yanis Kerdjana) entrent comme troisième source, lues dans `data/` de la branche `main` et datées du dernier commit qui y touche (API GitLab). La source n'a ni description, ni étoiles, ni dépôt : la description est composée en français depuis le pays, le tarif et les caractéristiques (tables de l'extracteur, qui reprennent les mots-clés de `classify.ts`), le score est estimé, et `alternative_a` vient de l'inversion de `sites-us.json`. Dix alternatives portent le nom d'un outil Praxis (Nextcloud, Mastodon, ONLYOFFICE, Collabora Online, CryptPad, Mattermost, Jitsi Meet, Matomo, OpenProject, Penpot) et ne sont pas importées, `nom` étant la clé unique ; Plans d'Apple, américain selon la source, est exclu ; GitLab est relié à Code FACiLe par `voir_aussi`. Nouveau champ facultatif `pays` (code ISO de l'éditeur tel que la source le donne), transmis au modèle et compté au sommaire. Cinq catégories que Praxis n'avait pas sont déclarées par l'extracteur (paiement en ligne, assistants d'intelligence artificielle, hébergement Web et infrastructure, commerce en ligne, diffusion audio et vidéo) et portent `source_repertoire_id` pour survivre à la resynchronisation de `update`, qui reconstruisait `categories.json` depuis la page. Quinze tags ajoutés à la main (hébergement en Europe, porté par un OSBL, certification de sécurité, sans publicité, écoresponsable, agenda et rendez-vous, VPN, développement logiciel, traduction, sans code, moteur de recherche, formation en ligne, téléphonie, gestion des correctifs, cartographie) ; les 52 tags sont tous utilisés après l'enrichissement. Enrichissement de 63 alternatives sur 72 (dont 2 après correction de leur lien ; 9 pages illisibles, retentées deux fois puis abandonnées à 3 échecs : Ecosia, Fnac, Mistral AI, Moodle et NordPass refusent le client, Pixelfed, Cdiscount, Olvid et Universign sont générées par JavaScript) ; 11 libres, 6 partiellement libres, 2 à code source disponible, 44 propriétaires. Avec cette source, la cible du répertoire s'élargit des OSBL des arts et de la culture aux organismes et aux petites équipes du Canada français : les consignes envoyées au modèle (fiche, évaluation, catégories, sommaire) le disent, les fiches existantes restent.

- **Constitution Spec Kit 1.0.0** (`.specify/memory/constitution.md`) : six principes tirés de ce que le dépôt applique déjà (les données d'abord, provenance et honnêteté, licences REUSE, coûts explicites, tests d'abord et simplicité, tout en français), les contraintes techniques, le flux de travail (un dossier `specs/NNN-nom/` remplace `IMPLEMENTATION_PLAN.md` et disparaît à la fin de la fonctionnalité) et la gouvernance (la constitution prime sur les gabarits, versionnage sémantique, modifications notées ici). Le fichier porte son propre en-tête SPDX, `.specify/**` étant annoté au nom de GitHub dans `REUSE.toml`.
- **Commits automatiques de Spec Kit** : les hooks de l'extension git commitent après chaque commande, et avant chacune sauf `/speckit-constitution` (vérification du dépôt Git) et `/speckit-specify` (création de la branche) : `auto_commit` est activé pour tous les événements dans `.specify/extensions/git/git-config.yml`, et tous les hooks de `.specify/extensions.yml` sont obligatoires (`optional: false`), si bien qu'une commande commite sans le demander au lieu de proposer `/speckit-git-commit` ; leurs messages fixes, en anglais à l'installation, sont réécrits en français et disent pourquoi le commit a lieu, pour respecter la constitution sans exception. `specs/**` est annoté dans `REUSE.toml` (documentation, `AGPL-3.0-or-later`).
- **Constitution 1.1.0, travail sur des branches** : le flux de travail impose une branche, plutôt que `main`, pour une fonctionnalité menée avec Spec Kit (`NNN-nom`), pour un changement de forme des données ou une rupture de compatibilité, et pour tout changement de code de plus d'un commit ; un changement d'un seul commit qui ne touche pas la forme des données peut encore aller sur `main`. Une branche est fusionnée quand `nub run test`, `nub run typecheck` et `nub run licences` passent, puis supprimée. Jusque-là, tout l'historique était linéaire sur `main`.
- **Site de consultation** ([`site/`](site/README.md), branche `001-site-consultation-repertoire`, première fonctionnalité menée avec Spec Kit : spécification, clarification, plan, tâches, analyse, implémentation, convergence). Un site statique en lecture seule pour les organismes et les petites équipes du Canada français : accueil qui liste les 154 outils par catégorie, une fiche par outil, filtres à choix multiple par catégorie, tag et statut du code source, recherche par nom, état des filtres dans l'adresse. La clarification a élargi la fiche au-delà de la demande initiale : trois lectures des critères (vérifiés avec citation, déduits des étoiles, second avis du modèle), pays de l'éditeur, logiciel derrière un service et données Open Hub. Le site lit les cinq fichiers JSON tels quels : ni leur forme, ni leurs schémas, ni les scripts n'ont changé. Chaque champ affiche sa provenance, les champs d'IA portent « à vérifier », un score estimé est dit estimé, et chaque page porte l'attribution CC BY-SA 4.0 et le crédit des autres sources. Les 12 outils non enrichis (la demande en annonçait 14) s'affichent avec les champs de leur source et leurs critères déduits, sans section vide. En cours de route, trois choix du plan ont été remplacés à la demande : les filtres sont une île SolidJS plutôt qu'un script sans cadriciel, daisyUI est importé en CSS seul plutôt que sur Tailwind, et Sätteri rend le Markdown à la place de `marked`. La convergence a relevé deux écarts, corrigés : le thème sombre n'était appliqué par aucune règle (les tests d'accessibilité « sombres » tournaient en clair), et les filtres par statut et par tag ne signalaient pas que ces champs viennent d'une IA. Validation : les 17 scénarios du guide de validation passent, par 62 tests unitaires, 34 tests du site bâti et 34 tests dans Chromium (filtres, adresse partagée, bouton précédent, lecture sans JavaScript, clavier seul, aucune violation axe A ou AA en thème clair et sombre, affichage à 360 px). Reste à décider : l'hébergeur, l'adresse publique et le déclenchement de la publication.
- **Interrupteur de thème** dans l'en-tête du site : clair ou sombre, d'après le « theme controller » de daisyUI dans un « swap » (soleil et lune). Il part du thème du système, retient le choix dans le navigateur et l'emporte ensuite sur le système ; sans JavaScript, il reste masqué et la page suit le système. Une première version à trois boutons (système, clair, sombre) a été remplacée le jour même par cet interrupteur à deux états.
- **Explorateur interactif** (branche `002-explorateur-outils`, deuxième fonctionnalité menée avec Spec Kit ; spécification, plan, contrats et tâches dans `specs/002-explorateur-outils/`). Une page « Explorer » pour les personnes qui comparent plusieurs outils avant d'en choisir un : tri par nom, score ou catégorie dans les deux sens ; filtres de la première tranche (catégorie, tag, statut, nom) et cinq de plus (score minimal, verdict de chaque critère vérifié, pays, source, enrichissement) ; mêmes résultats en cartes ou en tableau ; comparaison côte à côte de deux à quatre outils, au-dessus des résultats, avec les verdicts vérifiés et, sur une ligne à part, les critères déduits des étoiles ; tout l'état dans l'adresse. C'est une île SolidJS qui lit `explorateur.json`, écrit au build (104 ko, sans descriptions longues ni citations) ; chargement, erreur avec « Réessayer » et absence de JavaScript ont chacun leur message. La clarification a changé la première tranche : l'accueil devient une présentation du projet (répertoire, genèse, crédits, logiciels utilisés), la liste par catégorie passe sur une page « Outils » sans filtres, l'île de filtres de l'accueil est retirée, et chaque page porte la navigation « Accueil », « Outils », « Explorer ». Conséquence assumée : une ancienne adresse de l'accueil qui portait des filtres (`/?tag=…`) affiche maintenant l'accueil de présentation ; les liens de catégorie et de tag des fiches mènent à l'explorateur. Un `<noscript>` prévu au plan a été remplacé par un contenu d'attente toujours présent dans la page, parce qu'un navigateur où les scripts sont bloqués par un réglage ne l'affiche pas toujours. Validation : les 21 scénarios du guide passent, par 97 tests unitaires, 45 tests du site bâti et 79 tests dans Chromium (dont axe sans violation A ni AA sur l'explorateur en cartes, en tableau, avec une comparaison de quatre outils et en erreur, en thème clair et sombre, et l'affichage à 360 px).
- **Constitution 1.2.0, dossiers `specs/` conservés** : à la fin d'une fonctionnalité, son dossier `specs/NNN-nom/` n'est plus supprimé. Le contenu durable est toujours reporté dans `implementation.md` et ici, mais la spécification, le plan, les contrats et les tâches restent dans le dépôt, comme trace de ce qui a été demandé et décidé ; le code du site renvoie à ses contrats (`specs/001-site-consultation-repertoire/contracts/`). La version 1.0.0 prévoyait la suppression ; la question s'est posée à la fin de la première fonctionnalité.

## Décisions

| Décision | Raison |
|---|---|
| `update` est la seule porte d'entrée, import initial compris ; `build` est retiré | Tout ce que faisait `build` était déjà dans `update`, sauf l'amorçage et `criteres.json` ; une seule commande à connaître, et les opérations destructrices (`extract.ts --force`) restent explicites |
| Pas d'option `--enrichir` : `update` enrichit dès qu'un outil ne l'est pas, et met le sommaire à jour dès que quelque chose a changé ; pas d'option `--sommaire`, `--sans-sommaire` ni `--limite` | Une seule commande à connaître ; le consentement aux coûts se donne une fois, au premier import, et `--dry-run` chiffre avant de dépenser. Le sommaire coûte un appel, son résumé change à chaque exécution : il ne se refait que si quelque chose a changé |
| Jamais d'enrichissement sans page lisible (`--sans-page` retiré) | Un résumé tiré de la mémoire du modèle serait figé pour toujours ; mieux vaut un outil non enrichi, visible comme tel, abandonné après 3 échecs |
| Compteur `echecs_enrichissement` et abandon après 3 échecs consécutifs (`--max-echecs=N`) | Sans lui, les outils dont la page est durablement inaccessible étaient retentés à chaque exécution (délais et code de sortie 1), sans fin |
| `extract` (l'extracteur de Praxis) ne lit jamais de fichier HTML local et refuse d'écraser du travail sans `--force` ; `extract-facil.ts --fichier=` et `extract-charles.ts --dossier=` acceptent une copie locale de leur source | Un réimport détruit l'enrichissement et l'historique ; la page doit être l'unique source |
| Un outil enrichi n'est jamais régénéré | L'enrichissement coûte des appels à l'API ; pour le refaire, supprimer ses champs puis relancer |
| Les dates sont en heure de Toronto, avec le décalage | La page du répertoire donne l'heure de l'Est ; un horodatage avec décalage reste sans ambiguïté |
| Format strict des fichiers de données, sans reconnaissance de l'ancien format à plat | Un fichier au mauvais format est refusé avec un message clair plutôt que mal interprété |
| Schémas JSON générés par mion RunTypes et obuild, versions figées | RunTypes n'a pas atteint la version 1.0 ; les schémas commités sont vérifiés par `schemas:verifier` à chaque `nub run test` |
| Une alternative de Charles qui porte le nom d'un outil actif d'une autre source n'est pas importée, mais listée | `nom` est la clé unique de `outils.json` et celle des renvois `voir_aussi` ; un suffixe (« Nextcloud (Charles) ») casserait les renvois et ferait enrichir deux fois la même fiche |
| La description des alternatives de Charles est composée depuis les champs structurés de la source | La source n'a pas de description ; un texte tiré de la mémoire du modèle serait figé, alors que l'enrichissement, lui, lit la page de l'outil |
| Plans d'Apple exclu de l'import Charles | La source elle-même le dit américain (`country: "US"`), à rebours de son objet |
| Catégories déclarées par un extracteur, marquées `source_repertoire_id` | `update` reconstruit `categories.json` depuis la page Praxis : sans marquage, une catégorie ajoutée disparaissait à la synchronisation suivante |
| Champ `pays` facultatif, tel que la source le donne, sans table de noms | Le pays de l'éditeur est la donnée centrale de Charles et relève du critère « contrôle » ; un code brut reste réversible et vérifiable, le modèle le confronte à la page |
| Cible élargie aux organismes et aux petites équipes du Canada français, dans les consignes au modèle seulement | Les sources Charles (commerce, diffusion, assistants d'IA) dépassent les OSBL des arts et de la culture ; les 79 fiches déjà rédigées restent telles quelles |
| Les types des fichiers de données évitent `Date`, `Map` et les unions avec `Date` | RunTypes décrirait alors son propre encodage, pas le JSON naturel |
| `AGPL-3.0-or-later` pour le code et les schémas, CC BY-SA 4.0 pour les données et leurs dérivés | Les données adaptent le répertoire d'origine, publié sous CC BY-SA 4.0 ; conformité REUSE pour que chaque fichier déclare sa licence |
| `criteres` reste lié aux étoiles ; les critères vérifiés vont dans `criteres_confirmes` | Les étoiles sont une donnée de la source, les critères vérifiés dépendent de ce que la page de l'outil dit : aucune règle ne les fait coïncider sans sacrifier l'une des deux informations |
| Variantes de `classify.ts` essayées puis retirées (confiance recalibrée, retrait de critères) | Règles choisies en regardant les 57 outils enrichis ; l'une contredisait les étoiles, et `criteres_confirmes` répond au besoin |
| Critères vérifiés par le modèle de l'enrichissement (OpenAI), automatiquement dans `update`, plutôt que par un second modèle à la main | Une seule clé et un seul modèle, coût estimable par `--dry-run`, champ complet sans intervention ; l'indépendance du second modèle avait servi à l'analyse (accord sur 49 outils sur 57), et la citation vérifiable reste le garde-fou |
| Les catégories dans `categories.json`, référencées par identifiant | L'icône était répétée 60 fois pour 20 catégories, et un changement d'icône sur la page faisait bouger tous les outils de la catégorie ; la description de la catégorie a sa place dans ce fichier |
| Tests unitaires séparés des tests des données, lancés en parallèle par le runner | Les tests doivent passer sur un clone avant le premier `update` ; les fichiers de tests sont indépendants (fixtures, dossiers temporaires, port libre), donc un processus par fichier est sûr et deux fois plus rapide |
| Les deux environnements déclarés dans `package.json` (`engines`, `devEngines`) | Un seul fichier dit ce qu'exige l'exécution et ce qu'exige le développement ; nub provisionne le Node.js de `devEngines.runtime`, npm en avertit sans bloquer, et `.node-version` n'est gardé que pour fnm, nvm ou mise |
| Utiliser avec Node.js, développer avec nub | Un utilisateur ne doit installer que Node.js ; les scripts `update` et `sommaire` chargent `.env` eux-mêmes et n'ont besoin d'aucun outil de nub. Le développement garde nub pour la version de Node.js, le verrou des dépendances et les scripts ; un second verrou (`package-lock.json`) n'est pas maintenu |
| Graphiques en SVG, sans PNG | Les forges affichent les SVG autonomes dans le Markdown ; vectoriel net à toute taille, 8 fois moins lourd dans le dépôt, un appel vl-convert de moins par graphique. Seul l'export PDF par LaTeX y perd, personne ne le fait ici |
| Une source par outil (`source_repertoire_id`, `sources.json`), `update` ne synchronise que la sienne | Des outils venus d'ailleurs (FACiL, saisie manuelle) doivent survivre au suivi de Praxis, et chaque collection garde son extracteur et sa provenance (qui l'a soumise) |
| Concordance Open Hub par URL (page d'accueil, liens, dépôts), jamais par le seul nom | Un nom est ambigu (« Firefox », « Matomo » rendent des dizaines de projets) ; sans concordance sûre, mieux vaut lister les candidats que se tromper de projet |
| `gpt-6.1-sol` à effort `low` par défaut, `gpt-6-astra` en repli, une seule reprise par appel | Mesuré sur 20 outils (`analyse-effort/`) : Sol `low` donne les mêmes résultats qu'Astra pour un cinquième du prix, Terra en donne de plus prudents (champs à `null`, moins de critères) ; le repli, plus capable, ne paie que les réponses rejetées, et le coût reste prévisible (au plus deux appels) |
| Un service hébergé (FACiL) est une entrée distincte, décrite d'après son logiciel (`instance_de`) ; les doublons avec Praxis sont acceptés et reliés par `voir_aussi` | La page d'un service est souvent une page de connexion qui ne dit rien du logiciel ; le service garde son lien, ses alternatives et son hébergement au Québec, et le renvoi dit qu'il s'agit du même logiciel que l'outil de Praxis |
| User-Agent de navigateur, suivi du nom du projet et d'un contact | Certains sites refusent les clients sans en-tête de navigateur ; le nom et le courriel laissent un administrateur joindre l'auteur du dépôt |
| Le site est un sous-projet autonome (`site/`, son `package.json`, son `nub.lock`), sans dépendance ajoutée à la racine | Utiliser les données ne doit demander que Node.js ; Astro et ses dépendances ne concernent que qui bâtit le site |
| Le site lit les JSON tels quels et n'importe de la racine que des types | Les données sont le produit : le site les suit sans les changer, et un changement de forme casse sa vérification de types au lieu de passer inaperçu |
| SolidJS est la seule couche d'interactivité du site, limitée à une île pour les filtres ; les cartes restent du balisage statique | Le site doit se lire sans JavaScript ; une île qui rendrait la liste doublerait les données dans la page |
| daisyUI importé en CSS seul, sans Tailwind ni classe utilitaire ; variantes réactives retirées par un greffon PostCSS et interdites par un test | Pas d'étape de génération de classes ; la mise en page réactive est écrite une fois, dans le CSS du site |
| Sätteri pour rendre les descriptions longues, HTML brut remplacé par du texte | Les descriptions résument des pages tierces : le site n'insère jamais de HTML venu des données |
| L'adresse d'une fiche est le slug du nom de l'outil ; une collision arrête le build | `nom` est déjà la clé unique des outils ; aucun champ `id` à ajouter aux données |
| L'explorateur est le seul endroit du site où l'on filtre ; l'accueil présente le projet et la page « Outils » liste sans filtre | Deux endroits qui filtrent se contredisent tôt ou tard ; la liste statique reste pour qui n'a pas JavaScript |
| Les données de l'explorateur sont un fichier dérivé écrit au build et lu par le navigateur, sans descriptions longues ni citations | L'île ne reçoit que de la configuration ; le fichier reste léger sur un téléphone, et les fiches gardent le détail |
| Tout l'état de l'explorateur vit dans l'adresse, rien dans le navigateur | Une comparaison se discute à plusieurs : un lien copié doit restaurer exactement ce qu'on voit |
| Un outil non vérifié n'est retenu par aucun filtre de verdict, pas même « indéterminé » | « Indéterminé » est un verdict rendu après lecture de la page ; l'absence de vérification n'en est pas un |
| Publication du site non décidée ; adresse et chemin de base par variables d'environnement | Rien ne fixe encore l'hébergeur ; les liens internes passent tous par le chemin de base |
| Règle A pour « contrôle » : la nationalité mentionnée suffit | Les descriptions ne disent jamais qui possède l'entreprise ; sans convention, les IA divergent sur 21 outils. L'accord obtenu est une convention, pas une vérification de la propriété |
